What it is #

A large competitive-tuning mod for Puck: it exposes server- and client-side sliders for rule/competition settings (goal size and net tweaks, dash and spin behaviour, stick physics, arena tweaks), adds a "DashFall" server-editor UI so a server owner can change the live config, and syncs the resulting config to connected clients.

The DLL is the whole mod — no assets, no native libraries.

Code analysis #

Bootstrap. CompetitiveAdjustments/CompetitiveAdjustmentsGameMod.cs and DashFallMod/DashFallGameMod.cs implement IPuckPlugin. They register lifecycle patches explicitly — :11 [HarmonyPatch(typeof(NetworkManager), "StartHost")], :24 [HarmonyPatch(typeof(NetworkManager), "StartServer")], applied via :76 _lifecycleHarmony.CreateClassProcessor(typeof(StartHostPatch)).Patch() and :77, removed at :140 lifecycleHarmony.UnpatchSelf(). HarmonyPatchHelper.cs:15 Assembly.GetExecutingAssembly().GetTypes() + :39 harmony.CreateClassProcessor(type).Patch() patches the mod's own patch classes — this is the standard way to apply a large attribute-patch set from a BepInEx-style plugin, not dynamic assembly loading.

Harmony footprint: 183 patch attributes across many game types (rules, goal, puck, stick, dash, spin, arena, scoreboard, chat, vote manager, and the game's SynchronizedObjectRegistry sync path). That is the biggest behavioural surface in this set. It is a tuning mod, so this is expected — but it is a lot of game code being rewritten.

Admin/authorisation model — this is the part worth reading, and it is done properly.

  • AdminAuth.cs resolves admin status server-side only: host client 0 is admin; otherwise PlayerManager.GetPlayerByClientId(clientId) → AdminLevel.Value > 0; otherwise the game's own AdminManager.IsSteamIdAdmin(steamId) (NetworkBehaviourSingleton<ServerManager>.Instance.AdminManager, falling back to MonoBehaviourSingleton<AdminManager>). A client cannot assert that it is an admin.
  • The DashFall server editor is protected by an editor password: AdminAuth.GeneratePassword() produces 12 bytes from RandomNumberGenerator.Create() over a confusion-free charset, AdminAuth.VerifyPassword compares with a hand-written constant-time loop (num |= a[i] ^ b[i]), and AdminAuth.IsAllowed(clientId, password) grants access to admins or to a correctly-passworded client.
  • The admin config-set channel is verified on the server: PoncePuck.Keybinds/ServerBridge.cs:1083 OnAdminConfigSetMsg(ulong senderId, …) returns unless singleton.IsServer (:1090), reassembles the chunked payload, and then ServerBridge.cs:1105 if (!_authedClients.Contains(senderId)) { Debug.LogWarning("[COMPADJUST] Rejected PPKB/AdminConfigSet from un-authed client …"); … } else { ConfigApplyService.ApplyServerConfigEdit(text); … } — a real server-side authorisation check on the privileged path.
  • AdminAuth.AssertNoCredentials(string wireJson) refuses to transmit a config payload that contains "Admin" / "EditorPassword" keys, logging "BLOCKED: config wire payload contains credential keys; refusing to transmit." — the mod actively prevents its own credential from leaving the machine.
  • ChatManagerCommandPatch.cs:87 return AdminAuth.IsAdmin(clientId); gates mod chat commands server-side.

Findings #

  1. A privileged "server config edit" channel exists, but it is correctly authorised server-side (ServerBridge.cs:1083–:1123, :1105 _authedClients.Contains(senderId)). Only an admin (game admin list / AdminLevel > 0 / host) or a client that presented the correct editor password can push a config change. This is the design that 3735183385_Admin_Panel gets wrong. Severity: informational (positive).
  2. Editor password is stored in plaintext in the mod's config JSON (ConfigManager.cs:166 cfg.Admin.EditorPassword = AdminAuth.GeneratePassword(), generated with RandomNumberGenerator and compared in constant time). Plaintext-at-rest for a server settings password is normal for game mods, but it means anyone with read access to the server's config file can unlock the editor UI. Mitigated by AdminAuth.AssertNoCredentials refusing to transmit it. Severity: low.
  3. Copies the config JSON to the clipboard with the password redacted (DashFallClientRunner.cs:3330). Write-only; the mod never reads the clipboard. Severity: low.
  4. Deletes config files (ConfigManager.cs:234, :271, DashFallConfigLoader.cs:88). Scoped to the mod's own config JSONs under the game's config folder, but it is a delete path a user should be aware of. Severity: low.
  5. 183 Harmony patches across the game's rules, sync and physics code. Expected for a competitive-tuning mod, but it is the broadest patch surface in this set, can change match outcomes, and will break after a game update. Severity: moderate (the caveat in the verdict).
  6. One internal unsafe Netcode serializer (ConfigSyncPackage.cs:27). Managed unsafe pointer arithmetic inside a Unity serializer, not unmanaged code — but worth noting it is the only memory-unsafe code in the mod. Severity: low.
  7. Automated scan artefacts explained. hits_summary.txt records 2 magic-signature hits (CompetitiveAdjustments.dll offset 0 MZ — the DLL's own header — and offset 212,026 ZIP, an ordinary byte coincidence in compressed .NET metadata) and 0 keyword hits; text hits: 0. The binary string "Cryptography" at offset 299,037 is the metadata reference to System.Security.Cryptography pulled in by AdminAuth.cs:2. Severity: informational.

Bottom line #

Keep, with a caveat. It is a big tuning mod with a lot of Harmony patches, but its privileged paths are properly built: admin status comes from the game's server-side admin list, the editor password is random and compared in constant time, the admin config-set channel checks the sender on the server, and the mod refuses to transmit its own credential. The caveats are ordinary ones — 183 patches, it deletes its own stale config files, it copies a password-redacted config to the clipboard, and the editor password lives in plaintext in the server's config file.
